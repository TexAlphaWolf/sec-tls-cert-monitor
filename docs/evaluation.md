# How it was measured

`python tools/evaluate.py` prints everything on this page. CI runs it on every push (with fewer samples) and fails if any parser field differs, if any corrupt input raises an unexpected exception, or if any scenario is diagnosed differently from what is expected. Everything is local: certificates are generated by the script (`cryptography` package) and served from `127.0.0.1`.

## 1. The X.509 reader against a reference

300 random certificates (seed 2026): RSA 2048 and 3072, P-256, P-384, P-521 and Ed25519 keys; 0 to 5 DNS names, wildcard names, IPv4 and IPv6 names; common names with non-ASCII characters, 60 characters long or absent; validity from 1990 to about 2080 (so both UTCTime and GeneralizedTime); serial numbers of 8 to 158 bits; CA, non-CA and no basicConstraints; self-signed and CA-signed; three signature hashes. Nine fields are compared with what `cryptography` reads (serial, both dates, common name, DNS names, IP names, CA flag, SHA-256 fingerprint, key type and size).

**Result: 0 of 2,700 fields differ.**

**Caveat.** The reference is a different implementation, which is the point, but both read certificates made by the same generator. Real certificates in the wild have odd corners; the Live workflow (badssl.com has hosts with 1,000 names, no common name, an empty subject and an 8192-bit key) is the check for that. The SHA-1 and MD5 signature algorithms cannot be produced by current `cryptography`, so the tests rewrite the algorithm identifier of a real certificate; the parser does not check signatures, so this tests naming only.

## 2. Corrupt input

The parser reads bytes from a remote server, so it must refuse garbage without crashing. 20,000 inputs made from real certificates by flipping 1 to 6 bytes, truncating, inserting 1 to 8 random bytes or deleting up to 20.

| | |
|---|---|
| parsed anyway (a flipped byte inside a name still leaves a valid certificate) | 2,354 |
| refused with `DerError` | 17,646 |
| any other exception | **0** |
| slowest single parse | under 2 ms |

## 3. Diagnoses

Eighteen servers, each wrong in one known way, plus four faults that are not TLS configurations. For each, the expected grade and the exact set of findings (information-level ones aside) are compared with what `check` reports, through real handshakes.

**Result: 22 of 22 as expected** on Python 3.12 / OpenSSL 3.0.13 and on Python 3.14 / OpenSSL 3.5.7. The scenario list is printed by the tool.

**Caveats.**

- I wrote the expectations from the same rubric the code implements. This shows the implementation matches the rubric, not that the rubric is wise.
- Client and test servers are both OpenSSL. A server stack that fails differently (an F5, a Java server, a closed-source device) is the Live workflow's job.
- RC4 and 3DES are not in the matrix because this OpenSSL cannot offer them (see [limitations](limitations.md)).

## 4. Speed

Loopback only, so network latency is excluded. One host with all probes takes 9 connections here (11 where RC4 and 3DES can be offered): 36 ms (Python 3.12, OpenSSL 3.0) to 19 ms (Python 3.14, OpenSSL 3.5). 24 hosts, 8 at a time: 0.82 s and 0.36 s. Over the internet every connection pays round trips, so plan on seconds per host and keep `--interval` generous.

## Things the tests found while writing it

They are listed because they are what a reviewer should know the suite is for:

- A server that only speaks TLS 1.0 was reported as **unreachable**, because the first handshake used a modern client. It is now retried with a legacy client and graded F with its reasons. Test: `test_a_server_stuck_on_tls10_is_reported_not_unreachable`.
- OpenSSL's `UNSUPPORTED_PROTOCOL` was classified as "this machine cannot offer it". A client also gets it when the *server* answers with a version outside the range offered, so it is now treated as a refusal by the server.
- A 1024-bit RSA certificate made the first handshake fail at the default security level, so there was nothing to report. The inspecting client now runs at security level 0, and the report says separately that a normal client refuses the certificate.
- A handshake with an anonymous cipher has no certificate; it was treated as an error instead of as the finding it is.
- `[::1` (no closing bracket) was accepted as an address.
- In the first run of the scenario matrix three results were wrong, and none was a tool bug: the OpenSSL string `aNULL` also contains the suite `AECDH-NULL-SHA` (so it is correctly reported as both anonymous and NULL-encryption), `eNULL` also contains an RSA key-exchange suite, and my "silent server" closed the connection instead of staying silent. A fourth difference appeared on OpenSSL 3.5, whose default server cipher list no longer includes RSA key exchange; the scenario now asks for it explicitly.
